# 最小多设备协作开发计划

## 1. 目标

让本地笔记本与服务器成为对等工作节点：任一设备都可以完整修改、提交和接手项目，设备之间只通过 Git 交换可交接状态。

服务器拥有运行测试和实验的环境，但不拥有项目本身。大型数据、日志、checkpoint 和输出产物保留在产生它们的设备，不做自动同步。

## 2. MVP 原则

- Git 中已 commit 且已 push 的内容，才是其他设备可接手的项目状态。
- 每个任务使用一个 `work/<short-name>` 分支；不建立本地分支、服务器分支或任务状态机。
- 同一任务同一时间只在一个设备上继续；通过明确 handoff 后再切换设备，不实现锁或租约。
- 接手前 fetch 并更新分支；交接前提交全部必要文件并 push。
- 本地没有开发环境时可以完成调研、写作和代码修改，但必须如实标记“未运行”；验证留给有环境的设备。
- 不使用 Dropbox、网盘、SSH/rsync 或共享文件夹同步仓库工作区。
- 不同步大型数据和输出，只在必要时提交精简的结果、位置与复现信息。

## 3. MVP 范围

本阶段实现：

1. 初始化 Git，并连接一个私有远端 `origin`。
2. 在 `AGENTS.md` 中加入最小多设备协作规则。
3. 增加 `.gitignore`，排除环境、缓存、大型数据和实验输出。
4. 增加一个 repo-local `git-handoff` skill，让每台设备上的 Codex 使用相同的接手与交接步骤。
5. 在本地与服务器各做一次 clone、push、fetch 和接手验证。

本阶段不实现：

- DVC、对象存储、Git LFS、MLflow、W&B、CML 或 CI。
- 自动实验调度、远程命令执行或服务器连接配置。
- 任务卡、复杂状态流、所有权锁、租约或心跳。
- Git 镜像、故障切换、自动回退或自动冲突解决。
- 自动 commit、自动 merge 或 force-push。
- 大型数据、checkpoint、日志和输出产物的跨设备同步。

## 4. 目标文件

```text
AGENTS.md
.gitignore
.agents/
  skills/
    git-handoff/
      SKILL.md
docs/
  minimal-distributed-workflow-plan.md
```

MVP 不增加辅助脚本。先用简短、明确的 Git 命令验证协议；出现重复错误后再决定是否自动化。

## 5. Codex 开发步骤

### 步骤 1：补充仓库规则

修改 `AGENTS.md`，加入以下约束：

- 所有设备是对等节点，不设权威工作设备。
- 开始工作前读取 `AGENTS.md`、当前 session note 和相关实验文档。
- 开始或接手任务前执行 fetch，确认工作区干净，并更新目标分支。
- 一项任务对应一个 `work/<short-name>` 分支。
- 交接必须留下可理解的 commit 并 push；不得用未提交文件或 stash 交接。
- 无环境的设备不得声称已经通过测试。
- 大型数据和输出留在产生它们的设备，不纳入 Git 同步。

不要把具体 Git 命令、长模板或异常处理全部塞入 `AGENTS.md`；详细接手步骤放入 skill。

### 步骤 2：增加 `.gitignore`

至少忽略：

- `.env`、虚拟环境、Python 缓存和工具缓存；
- 本地编辑器和系统文件；
- 原始或缓存数据目录；
- `outputs/`、`logs/`、`checkpoints/`、临时 run 目录；
- 常见模型权重和大型二进制文件。

不要忽略调研文档、实验配置、精简指标、结果摘要、论文图表源文件和 session notes。

### 步骤 3：实现最小 `git-handoff` skill

创建 `.agents/skills/git-handoff/SKILL.md`，只包含两个流程，不添加脚本。

#### 接手

1. 阅读仓库规则、相关 session note 和相关实验说明。
2. 检查当前工作区；存在未提交修改时停止并说明。
3. fetch `origin`。
4. 切换到已有任务分支并以 fast-forward-only 更新；新任务则从最新 `origin/main` 创建 `work/<short-name>`。
5. 查看最新提交和差异，确认唯一下一步后开始工作。

如果分支已经分叉，停止并报告差异；MVP 不自动 rebase、merge 或覆盖。

#### 交接

1. 检查本次改动，只保留当前任务范围内的文件。
2. 运行当前设备能够运行的检查；不能运行的检查明确记录为 `未运行`。
3. 按既有规则选择性更新当前 session note。
4. 创建内容完整、可理解的 commit 并 push 当前任务分支。
5. 返回分支名、commit SHA、验证情况、下一步，以及必要的本地输出位置。

skill 不负责 merge、删除分支、创建远端仓库或同步实验产物。

### 步骤 4：初始化 Git 与远端

1. 在当前目录初始化 Git。
2. 创建初始提交。
3. 添加用户指定的私有远端为 `origin`。
4. 推送 `main`。

远端 URL 是唯一需要用户提供的前置输入；Codex 不自行创建公开仓库。

### 步骤 5：双节点冒烟验证

按以下顺序验证一次完整交接：

1. 本地从 `origin/main` 创建测试工作分支，修改一个小型文档并 push。
2. 服务器 clone 或 fetch 该分支，读取 handoff 信息并继续修改。
3. 服务器 commit/push。
4. 本地 fetch 后确认可以完整看到服务器提交。
5. 删除测试性改动；保留真正有用的协作规则。

验证过程中不得传输数据集或实验输出。

## 6. 实验输出规则

实验输出保留在运行设备原位置。只有当结果会影响后续研究判断时，才在对应实验 `README.md` 中提交精简记录：

```text
Git commit:
运行设备:
配置或命令:
关键结果:
验证结论:
本地输出位置:   # 仅在后续可能需要时填写
```

路径只用于帮助同一设备上的后续 session 找回产物，不代表其他设备必须能够访问。失败实验同样保留有价值的结论，但不提交完整日志。

## 7. 验收标准

- 本地与服务器都能从同一个 `origin` 独立 clone、修改和 push 项目。
- 任一设备都能依据 `AGENTS.md` 和 `git-handoff` skill 接手已有任务分支。
- 一次跨设备交接不依赖聊天记录、stash 或未提交文件。
- 无开发环境的设备不会把未运行代码标记为已验证。
- 大型数据、日志、checkpoint 和输出不会出现在待提交文件中。
- 没有引入任务状态机、远程执行、产物同步或额外服务。

## 8. 后续演进条件

只有实际遇到以下问题时才扩展：

- 经常忘记接手或交接步骤：再增加轻量辅助脚本。
- 同一任务频繁并发冲突：再增加任务认领记录。
- 实验难以复现：再增加结构化 run manifest。
- 多台计算节点需要排队：再增加调度或 CI。
- 确实需要跨设备取得大型产物：再单独设计产物存储方案。

在问题出现前，不预先实现这些能力。
